Geth 节点会持续向控制台报告消息，方便用户实时监控 Geth 的当前状态。日志会指示 Geth 何时正常运行，以及何时需要注意。然而，对于新用户来说，阅读这些日志可能比较困难。本节将帮助您解读日志消息，以便更好地理解 Geth 的运行情况。

请注意，Geth 节点的日志消息种类繁多，涵盖了各种可能的情况。本节仅介绍部分常见消息。更多信息，请参阅 [Geth GitHub](https://github.com/ethereum/go-ethereum)、[Discord](https://discord.com/invite/WHNkYDsAKU) 或在 [ethereum.stackexchange](https://ethereum.stackexchange.com/) 上搜索。日志消息通常具有足够的自描述性，无需额外解释。

### 日志配置

日志消息默认显示在控制台。您可以在启动时向 Geth 传递 `--verbosity` 和一个 0 到 5 之间的值，以调整消息的详细程度(默认是 3):
```s
0 = silent (no log messages)
1 = error (error messages only)
2 = warn (error messages and warnings only)
3 = info (error messages, warnings and normal activity logs)
4 = debug (all info plus additional messages for debugging)
5 = detail (all info plus detailed debugging messages)
```

日志消息也可以重定向，以便将其保存到文本文件中，而不是显示在控制台中。在 Linux 中，语法 `>> <path> 2>&1` 会将 `stdout` 和 `stderr` 消息重定向到 `<path>`。例如:
```s
# saves detailed logs to path/eth.log
geth --verbosity 5 >> /path/eth.log 2>&1
```

### 启动

Geth 启动后会立即报告一页相当长的配置详细信息和状态报告，以便用户确认 Geth 是否连接到正确的网络并以预期模式运行。日志消息的基本结构如下:
```s
MESSAGE_TYPE [MONTH-DAY][TIME] MESSAGE VALUE
```
其中 `MESSAGE_TYPE` 可以是 `INFO`、`WARN`、`ERROR` 或 `DEBUG`。这些标签根据日志消息的用途对其进行分类。`INFO` 消息告知用户 Geth 的当前配置和状态。`WARN` 消息用于提醒用户注意影响 Geth 运行方式的细节。`ERROR` 消息用于提醒用户存在问题。`DEBUG` 消息用于与故障排除或 Geth 开发人员相关的消息。

### 同步

Geth 默认使用 snap 模式进行同步。这需要共识客户端向 Geth 提供区块头。然后，该区块头将作为同步的目标。Geth 会向其作为目标节点的父节点请求区块头，直到形成一条足够长度的连续区块头链。之后，Geth 会为每个区块头请求区块主体和收据，并同时开始下载状态数据。这些状态数据以 [Patricia Merkle Trie](https://ethereum.org/developers/docs/data-structures-and-encoding/patricia-merkle-trie/) 的形式存储。只需下载该 trie 的叶子节点，然后从叶子节点开始在本地重新生成完整的 trie 结构。与此同时，区块链继续运行，目标区块头也会更新。这意味着一些重新生成的状态数据需要更新。这被称为`修复(healing)`。

假设 Geth 拥有一个已同步的共识客户端和一些对等节点，它将开始导入区块头、区块主体和收据。数据下载的日志信息如下所示(xxxxxx):
```s
INFO [07-28|10:29:49.681] Block synchronisation started
INFO [07-28|10:29:50.427] Imported new block headers               count=1    elapsed=253.434ms number=12,914,945 hash=ee1a08..9ce38a
INFO [07-28|10:30:00.224] Imported new block receipts              count=64   elapsed=13.703s   number=12,914,881 hash=fef964..d789fc age=18m5s     size=7.69MiB
INFO [07-28|10:30:18.658] Imported new block headers               count=1    elapsed=46.715ms  number=12,914,946 hash=7b24c8..2d8006
INFO [07-28|10:30:21.665] Imported new state entries
```

对于状态同步，Geth 会报告状态修复何时进行。这可能需要很长时间。日志消息包含当前修复阶段已下载的accounts(账户)、slots(时隙)、codes(代码)和nodes(节点)的数量，待处理(pending)字段表示等待下载的状态条目数。待处理值(pending)不一定是修复完成前剩余的状态条目数。随着区块链的进展，状态 trie 会更新，因此修复 trie 所需下载的数据可能会随时间增加或减少。最终，状态修复的速度应该快于区块链的进度，以便节点能够同步。状态修复完成后，会有一个同步后快照生成阶段。在状态修复阶段结束之前，节点不会同步。如果节点仍在定期报告`State heal in progress`(状态修复正在进行中)，则表示尚未同步 - 状态修复仍在进行中。

```s
INFO [07-28|10:30:21.965] State heal in progress                   accounts=169,633@7.48MiB  slots=57314@4.17MiB    codes=4895@38.14MiB nodes=43,293,196@11.70GiB pending=112,626
INFO [09-06|01:31:59.885] Rebuilding state snapshot
INFO [09-06|01:31:59.910] Resuming state snapshot generation root=bc64d4..fc1edd accounts=0 slots=0 storage=0.00B dangling=0 elapsed=18.838ms
```

可以使用 `eth.syncing` 确认同步 - 如果节点已同步，它将返回 `false`。如果 `eth.syncing` 返回 `false` 以外的值，则表示同步尚未完成。通常，如果同步仍在进行中，`eth.syncing` 将返回如下所示的区块信息:

同步过程中还经常会看到其他一些日志消息。例如:
```s
  WARN [09-28|11:06:01.363] Snapshot extension registration failed
```
此警告无需担心 - 它报告的是节点与对等节点之间的配置不匹配。这并不意味着同步停滞或失败，而只是导致对等节点被丢弃并替换。

```s
# consensus client has identified a new head to use as a sync target - account for this in state sync
INFO [10-03|15:34:01.336] Forkchoice requested sync to new head    number=15,670,037 hash=84d4ec..4c0e2b
```
上述消息表明，由共识客户端运行的分叉选择算法已确定 Geth 应同步到的新目标。这会重定向同步操作，以防止同步到过时的目标，这是同步实时区块链的正常步骤。

### 交易日志

通过本地 IPC、Websockets 或 HTTP 连接提交的交易会在控制台日志中报告。例如，一笔简单的 ETH 交易在控制台日志中显示如下:
```s
  INFO [09-06|01:31:59.910] Submitted transaction             hash=0x2893b70483bf1791b550e5a93763058b0abf7c6d9e6201e07212dbc64d4764532 from: 0xFB48587362536C606d6e89f717Fsd229673246e6 nonce: 43 recipient: 0x7C60662d63536e89f717F9673sd22246F6eB4858 value: 100,000,000,000,000,000
```

其他用户操作也有类似的日志消息显示到控制台。

### 常见警告

Geth 在正常运行过程中可能会发出许多警告。然而，在 Geth 的 [GitHub](https://github.com/ethereum/go-ethereum) 和 [Discord](https://discord.com/invite/WHNkYDsAKU) 频道上，有些警告被问到得尤其频繁。

```s
  WARN [10-03|18:00:40.413] Unexpected trienode heal packet          peer=9f0e8fbf         reqid=6,915,308,639,612,522,441
```
上述信息经常被误认为是快照同步的问题。实际上，它表示请求超时，可能是由于 I/O 速度慢造成的。这通常不是什么问题，但如果此消息在较长时间内频繁出现，则可能是本地连接或硬件问题。

```s
  WARN [10-03|13:10:26.441] Post-merge network, but no beacon client seen. Please launch one to follow the chain!
``
当 Geth 在合并后的权益证明网络上运行时，如果未安装共识客户端，则会发出上述消息。由于以太坊已迁移到权益证明网络，因此仅靠 Geth 不足以跟踪整个区块链，因为共识逻辑现在由一个称为共识客户端的独立软件实现。当缺少共识客户端时，会显示此日志消息。有关更多信息，请参阅我们的[共识客户端页面](https://geth.ethereum.org/docs/getting-started/consensus-clients)。

```s
  WARN [10-03 |13:10:26.499] Beacon client online, but never received consensus updates. Please ensure your beacon client is operational to follow the chain!
```
上述消息表明共识客户端已存在但无法正常工作。最可能的原因是客户端尚未同步。等待共识客户端同步应该可以解决问题。

```s
  WARN [10-03 | 13:15:56.543] Dropping unsynced node during sync    id = e2fdc0d92d70953 conn = ...
```
此消息表示某个对等节点由于未完全同步而被丢弃。这是正常现象 - 所需的数据将由其他对等节点请求。
