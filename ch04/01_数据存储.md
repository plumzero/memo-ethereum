自 v1.9.0 版本起，Geth 将其数据库分为两部分。近期区块和状态数据保存在快速访问存储中，而较旧的区块和收据("ancients")则存储在"freezer"数据库中。这种分离的目的是为了最大限度地减少对昂贵且敏感的 SSD 的依赖，并将访问频率较低的数据推送到更便宜、更耐用的硬盘支持的数据库中。在速度更快的 LevelDB 数据库中存储较少的数据，还可以实现更快的压缩，并通过在给定缓存大小的情况下允许更多状态 trie 节点存储在活动内存中来提高数据库性能。

### 近期区块

Geth 将最近的区块存储在 LevelDB 数据库中。这是一个持久化的键值存储系统，可以快速查询。LevelDB 数据库运行在高速 SSD 硬盘上，这样磁盘 IO 就不会受到底层硬件的瓶颈限制。除了基本存储功能外，LevelDB 数据库还支持按二进制字母顺序对键空间进行批量写入和迭代。数据库会定期压缩，以降低访问单个数据项的操作成本。这是通过扁平化给定键值范围的底层数据存储来实现的。该键值范围内任何已删除或覆盖的数据项都将被移除，剩余数据将被重新组织以提高效率。

Geth 还跟踪 LevelDB 数据库的几个性能指标，这些指标可以通过指标子系统进行监控。这些指标包括:

| 指标 | 功能 |
|:----|:-----|
| compTimeMeter | 用于测量数据库压缩总时间 |
| compReadMeter | 用于测量压缩过程中读取的数据量 |
| compWriteMeter | 用于测量压缩过程中写入的数据量 |
| writeDelayNMeter | 用于测量数据库压缩导致的写入延迟数量 |
| writeDelayMeter | 用于测量数据库压缩导致的写入延迟时长 |
| diskSizeGauge | 用于跟踪数据库中所有层级大小 |
| diskReadMeter | 用于测量有效读取数据量 |
| diskWriteMeter | 用于测量有效写入数据量 |
| memCompGauge | 用于跟踪内存压缩次数 |
| level0CompGauge | 用于跟踪level0中表压缩次数 |
| nonlevel0CompGauge | 用于跟踪non0层级中表压缩次数 |
| seekCompGauge | 用于跟踪由读取操作导致的表压缩次数 |

### freezer/ancients

较旧的链段会从 LevelDB 数据库移出，并移至冻结数据库。节点很少需要访问这些文件，因此 IO 速度不再那么重要，并且大部分链数据可以存储在更便宜的 HDD 上。一旦区块超过某个阈值年龄(默认为比头部晚 90,000 个区块)，区块和收据数据就会被扁平化，并保存为原始二进制数据块，同时保存一个用于识别的索引条目文件。

Geth 还跟踪一些与 ancient 数据库相关的可监控的基本指标:

| 指标 | 功能 |
|:----|:-----|
| readMeter | 用于测量有效读取数据量 |
| writeMeter | 用于测量有效写入数据量 |
| sizeGauge | 用于跟踪所有冻结表总大小 |

ancient 数据与快速访问的新数据完全分开保存，这意味着它们可以存储在不同的位置。ancient 链段的默认位置位于 `chaindata` 目录内，该目录位于 `datadir` 中，但可以在启动时向 Geth 传递 `--datadir.ancient <path>` 来定义它。freezer 的读取操作复杂度设计为 O(1)，仅涉及索引项（6 字节）的读取和数据的读取。这种设计使 freezer 的性能足以在慢速 HDD 磁盘上运行，从而允许人们在不需要大容量 SSD 的情况下运行以太坊节点。您也可以稍后通过手动将目录复制到新位置，然后启动 Geth 并将新路径传递给 `--datadir.ancient` 来移动 ancient 数据。

### 使用 freezer

如果 Geth 找不到 freezer（无论是因为数据库被删除还是 Geth 收到了错误的路径），节点都会变得不稳定。明确禁止使用无效的 freezer 路径启动 Geth。但是，如果状态数据库丢失，Geth 可以根据 freezer 中的数据重建所有索引，然后在其上执行快照同步以填充丢失的状态数据。

这可以用来主动清理节点。传递 `--datadir --removedb` 即可启动该过程。Geth 会询问是否应该删除状态数据库、旧数据库和 LES 数据库。选择删除状态数据库只会在 freezer 中保留完整的区块主体、收据、区块头等，这意味着重建状态不会涉及从网络重新下载约 400GB 的数据。然后，Geth 将使用现有的区块和收据数据从 freezer 中重建状态。在此过程中，未使用的数据和累积的垃圾数据将从状态数据库中删除。此过程可能需要一个小时或更长时间。

### 非正常关机

如果 Geth 意外停止，数据库可能会损坏。这被称为"非正常关机"(unclean shutdown)，它会导致节点重启时出现各种问题。最好始终以正常方式关闭 Geth，例如使用关机命令，例如 `ctrl-c`、`docker stop -t 300 <容器 ID>` 或 `systemctl stop`（但请注意，`systemctl stop` 的默认超时时间为 90 秒 - 如果 Geth 的正常关闭时间超过此值，它将被强制退出。请更新 `systemd.service` 中的 `TimeoutSecs` 变量，将此值覆盖为更大的值，至少为 300 秒）。这样，Geth 就知道需要将所有相关信息写入数据库，以便节点稍后正常重启。这可能需要将超过 1GB 的信息写入 LevelDB 数据库，这可能需要几分钟时间。

如果发生意外关机，可以使用 `removedb` 子命令删除状态数据库并将其与旧数据库重新同步。这应该可以使数据库恢复正常运行。

### Peddle

可以将 Geth 配置为使用 [Pebble](https://www.cockroachlabs.com/blog/pebble-rocksdb-kv-store/) 而不是 LevelDB 来存储近期数据。包含替代数据库的主要原因是 LevelDB 的 Go 实现并未得到积极维护，而 Pebble 是一个积极维护的替代方案，应该可以提供更好的长期选择。目前还没有迫切需要切换数据库类型的理由——LevelDB 运行良好，并且 Pebble 仍在评估未来某个时候是否可能取代 LevelDB 作为默认选项。但是，如果您想尝试使用 Pebble 运行 Geth，请在 Geth 启动命令中添加以下标志:
```s
  --db.engine=pebble
```

这还需要在新的数据目录中从头开始重新同步，因为如果启动时检测到现有的 LevelDB 数据库，Geth 将默认使用该数据库，并覆盖 `--db.engine=pebble` 标志。Pebble 仅适用于 64 位系统。
