注意: 离线剪枝仅适用于基于哈希值的状态方案。很快，我们将推出基于路径的状态方案，该方案将默认启用该剪枝功能。一旦不再支持基于哈希值的状态方案，离线剪枝功能将被弃用。

一个 snap-sync 同步的 Geth 节点目前需要超过 650 GB 的磁盘空间来存储历史区块链数据。使用默认缓存大小，数据库每周会增长约 14 GB。这意味着 Geth 用户很快就会耗尽 1TB 硬盘上的空间。为了在不购买额外硬件的情况下解决这个问题，可以对 Geth 进行修剪。修剪是指擦除旧数据以节省磁盘空间的过程。自 Geth v1.10 版本起，用户可以触发快照离线修剪，将总存储空间恢复到原来的约 650 GB。修剪时间取决于您的硬件，但可能需要 12 小时以上。必须定期执行此操作，以确保总磁盘存储空间在本地硬件的可用范围内（例如，对于 1TB 磁盘，大约每月一次）。

要修剪 Geth 节点，建议至少保留 40 GB 的可用磁盘空间。这意味着修剪无法用于保存已完全填满的硬盘。一个好的经验法则是在节点填满可用磁盘空间的约 80% 之前进行修剪。

### 修剪原则

- 1.请勿尝试修剪存档节点。根据定义，存档节点需要维护所有历史数据。
- 2.确保待修剪磁盘上至少有 40 GB 的可用存储空间。据报告，在剩余空间约为 25 GB 时，可能会发生故障。
- 3.Geth 至少为 v1.10，理想情况下大于 v1.10.3
- 4.Geth 已完全同步
- 5.Geth 已完成创建至少 128 个区块前的快照。当日志中不再报告"state snapshot generation"时，即为已完成。

满足这些原则后，即可修剪 Geth 的数据库。

### 修剪的工作原理

修剪使用状态数据库的快照作为指标，以确定状态 trie 中哪些节点可以保留，哪些节点已过时并可以丢弃。Geth 根据存储的快照层来识别目标状态 trie，该快照层顶部至少有 128 个区块确认（用于在重组后幸存），其中包含不属于目标状态 trie 或创世状态的数据。

Geth 分三个阶段修剪数据库:
- 迭代状态快照: Geth 迭代最底层的快照层，并构建一个布隆过滤器集，用于识别目标 trie 节点。
- 修剪状态数据: Geth 从数据库中删除不在布隆过滤器集中的过时 trie 节点。
- 压缩数据库: Geth 整理新数据库以回收可用空间。

在压缩数据库阶段，可能会有超过 1 小时的时间没有任何日志消息。这是正常现象，修剪过程应该继续运行，直到最终出现一条包含"State pruning successful"字样的日志消息（即，请勿重启 Geth！）。这条消息表示修剪已完成，可以启动 Geth 了。

### 修剪命令

对于正常的 Geth 节点，应停止 Geth 并执行以下命令来启动离线状态修剪:
```s
  geth snapshot prune-state
```

对于使用 systemd 运行的 Geth 节点:
```s
  sudo systemctl stop geth # stop geth, wait >3mins to ensure clean shutdown
  tmux # tmux enables pruning to keep running even if you disconnect
  sudo -u <user> geth --datadir <path> snapshot prune-state # wait for pruning to finish
  sudo systemctl start geth # restart geth
```

修剪可能需要 4-5 小时才能完成。完成后，请重启 Geth。

### 故障排除

关于"state snapshot generation"的消息表明快照尚未完全生成。这说明 `--datadir` 参数不正确，或者 Geth 没有足够的时间完成快照生成，导致修剪操作在快照完成之前就开始了。无论哪种情况，最好的处理方案是停止 Geth，然后恢复正常运行（不进行修剪），直到快照完全生成并且至少有 128 个区块，然后再尝试修剪。
